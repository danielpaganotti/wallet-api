# Wallet API

Backend service for a digital wallet: create wallets, register credit/debit
operations and query the statement (extrato). Built with Java 17 and Spring
Boot 3, backed by PostgreSQL, designed to be safe under concurrent traffic.

## Stack

- Java 17, Spring Boot 3.3.4 (Web, Data JPA, Validation, Actuator)
- PostgreSQL 16 (Docker), Flyway migrations (no `ddl-auto`)
- springdoc-openapi (Swagger UI)
- JUnit 5, Mockito, Testcontainers, Spring Boot Test

## Running it

### Option A — everything in Docker (recommended)

```bash
docker compose up -d --build
```

This starts PostgreSQL and the API. The app is reachable at
`http://localhost:8081` (mapped from the container's internal `8080`; the
host port is configurable in `docker-compose.yml`). It waits for Postgres to
report healthy before starting and runs Flyway migrations automatically on
boot.

Tear down with `docker compose down` (add `-v` to also drop the data volume).

### Option B — DB in Docker, app run locally

```bash
docker compose up -d db
./mvnw spring-boot:run
```

The app defaults to `jdbc:postgresql://localhost:5432/wallet_api` when run
this way (see `application.yml`); override with the `DB_URL`, `DB_USERNAME`,
`DB_PASSWORD`, `API_KEY` environment variables as needed.

### Authentication

Every endpoint (except `/actuator/health`, `/actuator/info`, Swagger UI and
the OpenAPI docs) requires a shared-secret header:

```
X-API-Key: changeme-local-dev-key
```

The expected value comes from the `API_KEY` environment variable (defaults to
`changeme-local-dev-key` for local use). Change it in `docker-compose.yml` or
your environment for anything beyond local testing. End-user auth
(JWT/OAuth) is explicitly out of scope for this challenge; this is a
service-to-service shared-secret gate, not a user identity system.

### API docs

Once running: `http://localhost:8081/swagger-ui.html` (or `/v3/api-docs` for
the raw OpenAPI JSON).

## Testing

```bash
./mvnw test
```

- **Unit tests** (`WalletServiceTest`, `TransactionServiceTest`): repositories
  mocked with Mockito. Cover wallet creation/lookup, credit, debit within and
  exceeding balance (insufficient-balance rejection), the exact-zero edge
  case, idempotent replay (same key + same payload), idempotency conflict
  (same key + different payload) and wallet-not-found.
- **Integration test** (`WalletTransactionIntegrationTest`): full Spring
  context + a real PostgreSQL instance via Testcontainers, driven through
  `TestRestTemplate` end to end — wallet creation, statement pagination,
  401/404/409/422 error paths, and a genuine multi-threaded race of 20
  concurrent debit requests against a wallet that can only satisfy 10 of
  them, asserting the final balance is exact and never negative.
  Requires a working local Docker daemon for Testcontainers.

Both concurrency scenarios below were also manually verified end-to-end
against the Dockerized stack with real parallel `curl` requests (see
"Concurrency strategy" for the results).

## Data model

**`wallets`**
| column | notes |
|---|---|
| `id` (UUID, PK) | generated by the service |
| `owner_name`, `owner_document` | optional titular info |
| `balance` NUMERIC(19,2) | never negative (DB `CHECK` + application logic) |
| `version` | optimistic-lock safety net (see below) |
| `created_at`, `updated_at` | |

**`wallet_transactions`** (the statement / extrato)
| column | notes |
|---|---|
| `id` (UUID, PK) | |
| `wallet_id` (FK) | |
| `type` | `CREDIT` \| `DEBIT` |
| `amount` NUMERIC(19,2) | always > 0 (DB `CHECK`) |
| `balance_after` | snapshot of the wallet balance right after this operation |
| `idempotency_key` | client-supplied key |
| `description` | optional |
| `created_at` | |

`UNIQUE (wallet_id, idempotency_key)` is the DB-level guarantee behind
idempotency (see below).

## API

| Operation | Route | Notes |
|---|---|---|
| Create wallet | `POST /wallets` | body optional: `{ "ownerName", "ownerDocument" }`. Returns 201, balance `0.00`. |
| Get wallet | `GET /wallets/{id}` | 404 if not found. |
| Register operation | `POST /wallets/{id}/transactions` | requires header `Idempotency-Key`; body `{ "type": "CREDIT"\|"DEBIT", "amount", "description"? }`. 201 on first success, 200 on idempotent replay. |
| Statement | `GET /wallets/{id}/transactions?page=&size=&from=&to=` | paginated (Spring `Pageable`), newest first; `from`/`to` are optional ISO-8601 instants filtering `created_at`. |

### Error format

Every error follows the same shape:

```json
{
  "timestamp": "2025-01-01T12:00:00Z",
  "status": 422,
  "error": "Unprocessable Entity",
  "code": "INSUFFICIENT_BALANCE",
  "message": "Wallet ... has insufficient balance: current=50.00, requested debit=999.00",
  "path": "/wallets/.../transactions",
  "details": []
}
```

| Situation | HTTP | `code` |
|---|---|---|
| Missing/invalid `X-API-Key` | 401 | `UNAUTHORIZED` |
| Wallet doesn't exist | 404 | `WALLET_NOT_FOUND` |
| Bean validation failure (bad body), missing `Idempotency-Key` header, malformed JSON | 400 | `VALIDATION_ERROR` / `MISSING_HEADER` / `MALFORMED_REQUEST` |
| Idempotency key reused with a different payload | 409 | `IDEMPOTENCY_KEY_CONFLICT` |
| Debit would overdraw the wallet | 422 | `INSUFFICIENT_BALANCE` |
| Anything unexpected | 500 | `INTERNAL_ERROR` |

**Why 422 for insufficient balance and not 400/409?** The request is
syntactically valid and well-formed (400 doesn't fit); it isn't a duplicate
or conflicting write (409 doesn't fit either). It's a semantically valid
request that cannot be *processed* because it violates a business invariant
— which is exactly what 422 Unprocessable Entity means.

## Concurrency strategy (the core of the challenge)

Two invariants must hold under concurrent traffic on the **same wallet**:
(a) the balance never goes negative, and (b) no operation is ever applied
twice. The design combines three layers, each covering a different failure
mode:

1. **Pessimistic row lock as the primary control.** Every write to a wallet
   goes through `WalletRepository.findByIdForUpdate`, which issues
   `SELECT ... FOR UPDATE` on the wallet row inside the same DB transaction
   used to check the balance, validate the debit, insert the transaction
   row and update the balance. Concurrent requests targeting the *same*
   wallet are fully serialized at the database: the second request blocks
   until the first commits or rolls back, and only ever sees a
   fully-consistent, post-commit balance. Requests against *different*
   wallets don't block each other — the lock is per-row, not per-table, so
   throughput isn't sacrificed for unrelated wallets.

   This was chosen over optimistic locking because wallet writes are
   expected to be short and contended exactly on hot wallets (the scenario
   the challenge calls out); pessimistic locking avoids the retry storms
   that optimistic locking would cause under real contention, at the cost
   of holding a lock for the (very short) duration of one transaction.

2. **Idempotency check happens *after* acquiring the lock, in the same
   transaction.** The check for an existing `(wallet_id, idempotency_key)`
   row, the balance validation, and the insert of the new transaction are
   all performed while holding the row lock — so there's no window where two
   concurrent requests with the same key can both pass the "does this key
   already exist?" check before either commits. Whichever request enters
   the critical section first wins; the other sees the just-inserted row
   and returns the original result instead of re-applying the operation.

3. **`UNIQUE (wallet_id, idempotency_key)` DB constraint as a safety net.**
   Even if the lock were ever bypassed by a future code path (e.g. a bulk
   job that forgets to go through `findByIdForUpdate`), the unique
   constraint makes a true double-insert impossible at the storage layer. A
   violation surfaces as `DataIntegrityViolationException`, translated by
   the global exception handler into `409 IDEMPOTENCY_KEY_CONFLICT`. A
   `CHECK (balance >= 0)` constraint on `wallets` gives the same kind of
   defense-in-depth for the non-negative-balance rule, and `@Version` on the
   `Wallet` entity adds an optimistic-lock tripwire in case anything ever
   updates the balance outside the locked path.

**Idempotency semantics:** the client sends an `Idempotency-Key` header with
every `POST .../transactions`. Replaying the *same* key with the *same*
`type`/`amount` payload returns the original transaction (`200 OK`, no
balance change). Reusing the key with a *different* payload is rejected
(`409 IDEMPOTENCY_KEY_CONFLICT`) rather than silently applied — silently
accepting it would mean the client's replay was ambiguous. Amounts are
compared after normalizing both to 2 decimal places, matching the persisted
precision.

**Manually verified** against the real Dockerized stack (not just unit
tests) by firing genuinely parallel requests with `curl &`/`wait`:

- 20 concurrent `DEBIT 10.00` requests against a wallet funded with `100.00`:
  exactly 10 succeeded (`201`), exactly 10 were rejected (`422`), final
  balance was exactly `0.00`, and exactly 11 transactions were persisted (1
  credit + 10 debits) — no double-application, no overdraft.
- 15 concurrent `POST` requests carrying the *same* `Idempotency-Key` and
  payload: exactly 1 returned `201` (all others `200`), all 15 returned the
  *same* transaction id, and the balance changed only once.

## Other decisions worth calling out

- **Amount precision:** all monetary values are `BigDecimal` with
  `NUMERIC(19,2)` in Postgres; incoming amounts are normalized to 2 decimal
  places (`HALF_UP`) before being persisted or compared.
- **Statement filtering:** `from`/`to` filters are implemented with a JPA
  `Specification` (rather than a single JPQL query with nullable
  parameters) because Postgres cannot infer the parameter type of a bind
  variable that's only ever compared against `NULL` in an `IS NULL` branch —
  building the predicate list conditionally avoids sending an untyped null
  parameter altogether.
- **Migrations:** two Flyway scripts (`V1` wallets, `V2` wallet_transactions);
  `spring.jpa.hibernate.ddl-auto` is `validate`, so the schema is never
  inferred/altered by Hibernate at runtime.
- **Out of scope**, per the challenge: multi-currency, FX, interest,
  end-user auth (JWT/OAuth), scheduled transactions, chargebacks, any
  frontend.
